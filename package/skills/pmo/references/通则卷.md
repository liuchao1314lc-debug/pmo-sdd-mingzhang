## 协议类

### 需求 ID 链与门禁（#1）

**是什么**：每个需求赋唯一 ID，从 MRD 贯穿迭代；回溯的固定抓手，检查产出物时沿 ID 链反向走，偏差与遗漏在链上显形。

**ID 方案**：

- 结构：〈类型码-序号〉，如 R-001；修订层派生为 R-001.1（需求变更原地改，#8）。**修订层专用**：R-001.N 仅表 R-001 的第 N 次变更，禁止兼作子需求编号；需求分解产生的子需求赋新 ID（R-002…），父子关系经产出物上游引用头部（#6）表达，不进 ID。
- 类型码封口：〈类型码-序号〉为全实体编号通则——需求 R；图 ID、产出物 ID、能力 ID 沿用同构，类型码各自主项定（#13／#6／#14），跨实体不混码。阶段实体类型码（F 功能／M 模块／CP 组件／S 屏／U 架构单元／P 开发包／DF 缺陷）统一定义并登记于本处（#1 类型码封口），沿用同构；阶段卡与模板只用不另定义，跨实体不混码。
- 唯一、稳定、不可复用：ID 一旦赋予不改不删，废止只标记（#3 已作废），号段不回收。
- 贯穿：MRD 赋 ID→PRD/架构/模块/组件/UI/开发/联调测试/迭代沿 ID 链引用；产出物头部需求 ID 必填（#6）。

**门禁**：产出物头部缺需求 ID 或上游引用即门禁不过（#20）；回溯沿 ID 链反向，经图集索引（#13）定位图。

**规则**：新增需求赋新 ID（纯增量），需求变更用修订层，bug 修复先归因（#8）；ID 方案本卷统一，项目实例化只定前缀不改结构。

### 裁定协议（#7）

**是什么**：所有门禁共用的四步统一协议；不允许各阶段另写一套。

**四步**：

1. **呈报**：agent 提出待裁项，大白话＋专业表述对照（语言转换点见 #11）；附独立检查者校验结果（裁定前先校验，#21）与证据。
2. **用户裁定**：用户用大白话给结论；agent 不自我裁定。
3. **记入决策域**：裁定内容、依据、大白话原文与专业表述对照写入 governance/决策记录；写入通道是本步专属动作（#20 执法校验一一对应）。
4. **生效并更新状态板**：按 #21 授予生效（已生效＝有决策记录），更新状态板（#9）当前阶段与待裁项。

**规则**：

- 裁定前必须先跑校验（检查者先于门禁，#21）。
- 高风险动作另需用户明确动作短语授权（项目卷 权-02／权-03）。
- 未裁定：项留状态板"待裁"，不生效、不进下一阶段；裁定否决：按 #3 待裁→草稿打回修订（如需废止则待裁→已作废），不生效。

### 重入协议（#8）

**是什么**：三类型＋统一流程；流程中途与交付后共用。

**三类型**：

- **新增需求**：赋新 ID 走全链（纯增量），不改旧基线。
- **需求变更**：原 ID 原地改＋受影响下游产出物与图标"待复核"（变更回流，下节）。
- **Bug 修复**：先归因裁定——执行偏差回开发（文档不动）；定义缺陷转需求变更。

**统一流程**：登记→裁定类型与重入点→执行→关闭。状态板记录打断与回归（#9）。

**变更回流**：沿 ID 链（#1）与图集索引（#13）把所有受影响下游产出物与图标"待复核"（文档状态词表 #3），保证回溯链变更后不失真。

**规则**：重入类型由用户裁定（#7），agent 不自判"这只是小修"；交付物版本升级与旧版保留按项目卷 版-01。

### 语义对齐（#11，语言转换点）

**是什么**：大白话↔专业语言转换＋术语对齐，两项原则合一。

**转换点固定**：在裁定协议呈报环节（#7 步 1）——与用户沟通用大白话；确认后的专业表述才入文档；大白话原文留决策记录作对照。

**术语对齐**：用户不同用词但同表意→定义对齐，入术语表（#2）同义词映射；新词先入表再使用（项目卷 信-04）。

**规则**：与用户沟通不堆术语、不用内部任务编号代替结论、汇报先给结论再展开；未经用户确认的专业表述不入已生效文档。

### 回退与跳阶段

**是什么**：线性流程的异常路径——跳阶段（向前）与回退（向后）；细则随十卡落定（本节）。与 #8 重入协议分工：#8 管变更类型与下游标记，本节管阶段间导航；回退由变更/bug 引起时调用 #8，不另立标记机制。

**跳阶段（向前）**：

- 哪些阶段可跳由强度档位定（#22 阶段遍历数维度）；本卷定机制与承重下限，具体跳过集随档位干跑测定，不在此定死（档位数是用户参数，#22）。
- 承重下限不掉（#22）：门禁判据可检查、ID 追溯不断。
- 跳过阶段的出口判据不免：并入下一保留阶段门禁核验；阶段未跳过则门禁照留。并入判据逐条显形——**并入核验**或**不适用（N/A）附理由**，记入门禁记录，不静默省略。对账判据（每外部能力需求必有处置状态，#17）承重，不因跳过而掉；MRD／架构出口对账门禁在阶段未跳过时不因降频而免（#22）。
- 示例（干跑测定，非硬规则）：轻档可合并模块/组件/UI 入开发，标/重档全遍历十阶段。

**回退（向后）**：

- 须裁定（#7）：回退目标阶段与范围由用户裁定，agent 不静默改下游、不自创回退路径。
- 由需求变更/bug 引起时调用 #8：类型裁定＋变更回流（沿 ID 链 #1 与图集索引 #13 把受影响下游已生效产出物与图标"待复核"#3），回溯链不失真。
- 回退目标阶段按该卡入口条件（#5）重入；上游已生效产出物为重入基线。
- 已生效兄弟产出物不重写：回退只影响目标阶段及其受影响下游，未被变更波及的兄弟阶段已生效产出物保留原状态（交付物版本升级与旧版保留按项目卷 版-01／版-04）。

**规则**：跳阶段/回退记状态板"打断与回归"（#9），当前阶段更新为实际导航目标；agent 不自创跳/退路径，承重下限不因导航而降。

### 保证机制（#21，生效授予与信任根）

**是什么**：承重地板，任何档位不掉。

**三权分立**：

- **生产权＝agent**：只出草稿，不自我生效。
- **校验权＝独立检查者**：只读、与生产者分离、不共享上下文；门禁前必跑（裁定前先校验）＋命令按需跑。
- **生效权＝用户**：裁定授予（#7）。

**信任根不变量**：已生效＝有对应决策记录，机械可查；决策记录写保护，agent 不能自我授予或伪造。

**承重条款（任何档位不掉）**：生效须裁定、四层隔离、单一事实源、状态板续接、ID 追溯。

**降级纪律**：降级不删条款、只降执法强度；凡降级触及信任根或承重条款执法（如宿主无 agents→独立检查者缺位→生效校验压回手工），不止写回执，须走 #7 呈报裁定、用户显式接受手工替代后部署方生效。

### 减重机制（#22，强度档位与承重/仪式划分）

**是什么**：承重讲纪律、仪式讲敏捷。

**承重层**＝#21 地板，永不降。

**仪式层缩放五维度（各标承重下限）**：

| 维度 | 缩放 | 承重下限 |
|---|---|---|
| 阶段遍历数（跳阶段） | 可跳过非必需阶段 | 门禁判据可检查、ID 追溯不断 |
| 图集 rigor（出图数/审批颗粒） | 按强度减图 | 节点映射与图集闭环（#19）不缺 |
| 对账频次 | 按强度调频 | 每个外部能力需求必有处置状态（#17），不空；MRD／架构出口对账门禁在阶段未跳过时不免 |
| 门禁颗粒度 | 按强度粗细 | 生效须裁定、裁定前先校验 |
| 文档体量 | 按强度精简 | 单一事实源、状态板续接、产出物上游引用头部 |

**强度档位**：启动选定、随工作显形可升档，记入治理配置＋决策记录；档位数与阈值是用户参数（示例 轻/标/重），干跑测定，本卷不替用户定死。示例（干跑测定，观察数据，非硬规则）：标档 MRD＝两批 MRD 裁定加一次收口执行；PRD/架构/模块/组件/UI 各 1 批（架构单批 4 裁定点）；轻档迭代重入不跑全链（内容面不变原地修订）；最小产品不触发数量分片。

**自动化配重**：hook/脚本是让承重保持轻的配重；降级代价＝同等保证压回手工（#21 降级纪律）。

## 图集类

### 分切与映射规则（#12）

**是什么**：图集＝可缩放树（地图册，非 1:1 地图）；纵向逐层细化，横向同层过大时分片。

**分切**：

- 纵向：起点＝MRD 需求级全景流程图（树根）→PRD 功能→架构→模块/组件/UI，逐层展开成子图。
- 横向：同层过大按需求 ID/模块边界分片，自树根展开。
- 判据：一张图只回答一个抽象层级的一个问题，禁止混层级；细节展开成子图，不堆进一张图。

**节点映射**：下游图节点强制标注上游出处（图 ID＋节点 ID）；上游节点声明在哪展开或到此为止；图集成为 ID 链的图形化表达，图与图不断链。跨图依赖可在消费端图画引用节点：出处锚提供端图的上游节点、本图注明登记图；引用节点不计本图覆盖成员，覆盖核销以登记图为准。

**规则**：同抽象层级检查（同父或同级兄弟图）防混层；分切与映射机械可查部分进 #20（图出处／层级／覆盖一致）；索引登记见 #13。

### 图集索引结构（#13）

**是什么**：每张图的登记簿；agent 查索引找图不扫全集，变更回流靠它定位受影响的图。

**条目字段（每图一条）**：

- 图 ID（沿用〈类型码-序号〉，如 G-001，与 R/C 分码，#1）
- 所属阶段
- 层级（抽象层级）
- 上游图及节点（图 ID＋节点 ID；边界图为根伴视图，单独标注）
- 覆盖需求 ID
- 位置（路径）

**规则**：

- 索引簿随首图出现建立，首图审批（#19）前完成索引登记；初始化模板包提供骨架。
- 索引是唯一导航入口；未登记进索引的图不算图集成员（闭环靠索引簿记，#19）。
- 索引只载指针，不载图内容与状态（项目卷 文-03）。
- 变更回流（#8）经"覆盖需求 ID"与"上游图及节点"定位受影响下游图，标待复核。
- 按需加载：沿"当前图→上游出处→相关兄弟图"，永不整集读入。

### 边界图与外部依赖规则（#14）

**是什么**：与缩放树并存的根伴视图，不进树层级序列；MRD 阶段建立，是产品与全部外部能力关系的唯一事实源。

**能力—载体两层**：

- 能力（如邮件收发）确定；载体（邮箱 API／MCP）状态：未定/已定/已替换。
- 允许"依赖存在、接入未定"为合法状态，防 MRD 过早写死实现。
- 能力变化与载体变化分开回流（#8）。

**外部边强制属性**：方向、接入形式、决策状态、决策引用——必填。载体未定时，决策引用＝批准本图生效的门禁裁定记录（能力确认、载体暂不定），不空。

**两类边两个映射**：内部边映射树内上游节点；外部边锚定边界图能力 ID。

**能力 ID 编号**：能力 ID 沿用〈类型码-序号〉（如 C-001），与需求 R 分码（#1 类型码封口）；载体状态词表（未定/已定/已替换）挂能力 ID。

**规则**：载体选择挂决策域（#7），边界图只呈报"定了没、定的什么、谁定的"；边界图审批用 #19 特殊替换；能力需求侧对账见 #18。

### 图审批规则（#19，三层闭环）

**是什么**：图生效前的三层闭环判据；审批走 #7 裁定。

**三层**：

- **对外**：输入输出明确（每条进出的边有来源/去向与属性）。
- **对内**：完整闭环——无孤儿/悬空节点，单一抽象层级不混（同父或同级兄弟图，#12）。
- **整体**：图集经索引簿记闭环（#13），非全读；每张图登记进索引才算图集成员。

**边界图特殊替换**：对外＝外部边属性齐全（#14）；对内＝能力—载体闭合；整体＝边界图登记进索引（根伴视图单独标注）。

**规则**：机械可查部分（出处层级一致、索引登记）进 #20 执法；语义判断（抽象层级合理性）留 rules＋方法；图未过审批不生效（#3）。

## 对账类

### 能力词表（#15）

**是什么**：需求侧与供给侧共用的能力定义；匹配变成同词对账而非语义猜测，保证复用指向准确。

**结构（每词一条）**：能力 ID＋规范名＋定义（一句话）＋同义词/别名。

**规则**：需求侧（边界图 #14）与供给侧（台账 #16）共用同一词表；新词准入经 #16 用户通道；内容结构归本项，写入权威归 #16 统管，不在此另挂；术语对齐方法同 #2／#11。

### 供给台账结构（#16，含环境供给层写权威）

**是什么**：环境级、跨项目能力资产登记簿；扫一次登记一次验证一次，后续项目对台账不重扫环境。

**条目字段**：

- 能力 ID（与能力词表 #15 对齐）
- 能力描述（能做什么）
- 载体（MCP／skill／API／现成模块等）
- 调用约束（输入输出／权限／额度等）
- 核实状态：声称有／已验证

**核实状态词表**：声称有＝供给方声称、未经本地验证；已验证＝本地真实调用核验通过。"已复用"必须"已验证"（#17），声称有不能写成已验证。

**环境供给层写权威（统管台账＋词表两资产）**：

- 登记、核实更新、标已替换、新词准入、词条修订归环境供给层写权威；此权威只在本项定义一次，#15 不另挂写权威。
- 项目侧 agent 只读台账、提交验证证据；写入/更新经此权威协议，跨项目共用，不单项目私改。
- **字段级双通道**：登记与验证证据追加＝agent 通道；核实授予（升"已验证"）、标已替换、新词准入、词条修订＝用户通道，经 #7 裁定写入。写保护落在授予字段，agent 通道与用户通道分离（与决策记录写入通道同款处理）。
- **证据口径**：验证证据按决-01（正式保存＋独立读回）；独立检查者可按需校验证据（#21 命令按需跑），不作强制第三步——环境层簿记不逐条开三权，与档位哲学一致。

**规则**：台账是环境级资产，不回流进 skill、不成项目私有事实；项目卷 权-01 引用本项写权威。

### 处置状态词表（#17）

**是什么**：每个外部能力需求必带的处置状态，不允许空。

**四态**：

- **已复用**：台账有且已验证（#16），直接复用。
- **待获取**：台账有但未验证/需接入，待获取验证。
- **自建**：台账无或有但不用，须举证（#18）。
- **待裁**：处置未定，呈报用户裁定（#7）。

**规则**：完整性靠"每个需求必有下场"保证，未处置项显形状态板（#9）；已复用必须已验证，声称有不算；对账产出需求×供给对账表（#18）。

### 对账协议（#18）

**是什么**：能力供需对账的统一流程；治"一遍遍重扫、扫完仍遗漏、造轮子"。

**门禁位置**：MRD 出口、架构出口跑对账（阶段未跳过时不免，#22）；产出需求×供给对账表。深度拆分（能力—载体两层在对账上的投影，#14）：MRD 答"有没有"（能力存在性），架构答"怎么接、接多少"（载体实现）。

**流程**：

1. 列需求侧能力（边界图 #14，能力词表 #15 规范名）。
2. 供给发现：先对供给台账（#16）同词匹配（#15），不语义猜测；台账不足时外部 prior-art 粗扫（GitHub/开源等已有实现）。外部候选经 #16 字段级双通道入台账——agent 通道登记"声称有"，要复用经用户通道核实授予"已验证"（#17 处置状态待获取→已复用天然接住）；不建"检索报告"新 artifact，发现进台账＋对账表两个既有载体（单一事实源）。
3. 每需求标处置状态（#17），不空。
4. 未处置/待裁项显形状态板（#9）。

**自建举证门禁**：裁定自建必须引用对账结果，证明台账与外部都没有、或有但为何不用；造轮子从默认行为变成需举证的特批行为（#7 裁定）。

**规则**：后续项目对台账不重扫环境（#16 扫一次登记一次验证一次）；对账频次按档位（#22），出口门禁本身不免。粗扫深度亦按档位（#22 仪式层）：轻档可只查台账，标/重档加外部检索；处置状态完整性下限不掉（与对账频次行同口径）。

## 词表与结构类

### 术语表（#2）

**是什么**：项目级术语单一定义登记簿；新词先入表，同义词对齐。

**结构（每词一条）**：

- 词条（规范名）
- 定义（一句话）
- 同义词/别名（用户不同用词但同表意，映射到规范名）
- 来源（首次出现的产出物/决策记录）

**术语钉死**：文档角色词钉死"长期规则"；项目实例化时旧称不入表，两称不并行。

**规则**：同词只一处定义（项目卷 信-01），其余文档引用规范名；新词先入表再用（项目卷 信-04），对齐动作在裁定呈报环节（#11）；术语表是项目事实，在 governance/，不回流进 skill。

### 文档状态词表（#3）

**是什么**：产出物/文档生命周期状态的统一词表。

**五状态**：

- **草稿**：agent 产出，未呈报裁定。
- **待裁**：已呈报，等待用户裁定（#7）。
- **已生效**：用户裁定授予，有决策记录（#21 信任根）。
- **待复核**：上游变更，受影响下游待重新核验（#8 变更回流）。
- **已作废**：被新版替代或明确废止，保留追溯，不再生效。

**转换规则**：

- 草稿→待裁：呈报附校验结果。
- 待裁→已生效：仅经 #7 裁定＋决策记录；agent 不能自行转换。
- 待裁→草稿：裁定否决，打回修订后重新呈报；如需废止则待裁→已作废。
- 已生效→待复核：上游需求变更（#8）。
- 已生效→已作废：新版生效或明确废止裁定；旧版保留（项目卷 版-01／版-04）。
- 待复核→已生效/待裁：复核通过或重新裁定。

**规则**：状态机械可查——已生效项必与决策记录一一对应（#20 执法）；已作废不删除，只标记。

### 版本记法（#4）

**是什么**：需求版本、交付物版本、产品发布版本三轨分离的记法。

**三轨**：

- **需求版本**：需求 ID＋变更序号（如 R-001、R-001.1），记需求演进，贯穿 ID 链（#1）。
- **交付物版本**：文档/产出物自身版本号（如 v1、v2 整数递增），记文档演进，已生效文档修改时升级（项目卷 版-01）。
- **产品发布版本**：整个产品对外发布的唯一号，采 SemVer `主.次.修订`（MAJOR.MINOR.PATCH），记对外发布事件。主＝不兼容变更、次＝向后兼容新功能、修订＝向后兼容修复；升高位低位归零，已发布内容不可改。SemVer 语义为行业标准、本卷定死，不做实例留白（区别于字符串前缀那类实例参数）。

**产品发布版本授予与升位**：

- **授予触发器＝用户明确授权的发布事务**（项目卷 权-02／权-03 动作短语）；联调测试出口、迭代只是发布事务的可能发生地，不是触发器；验收通过本身不授号（项目卷 版-03）。
- **升位判定在发布事务时点**，按自上次发布以来累计的 #8 重入类型判：新增需求→次、bug 执行偏差→修订、需求变更按兼容性→主或次；多类型并存取最高位，有不兼容变更即主；不是每次重入即升号。
- 主/次兼容性判定属语义判断，随发布裁定呈报、由用户裁（#7），不进 hook（#20 机械/语义分界）。
- **记录位置**：发布号入项目卷 版-02 身份 metadata 的版本标识＋状态板身份誊录（#9）；历史发布随决策记录追溯。

**规则**：

- 已生效交付物修改→交付物版本升级＋旧版保留＋引用上游需求版本（项目卷 版-01）；交付物版本升级不另设授权事件（"升版"消歧见项目卷 版-03）。
- 三轨互不混用：需求记需求演进、交付物记文档演进、发布版本记对外发布事件；经上游引用头部（#6）与版-02 身份关联，不共用一个号。
- 需求版本轨道 ID 部分沿用 #1，修订层语法由 #1 派生；R-001／R-001.1 与 #1 示例一致。
- 身份 metadata（版本标识、来源提交、生成时间、完整性校验）按项目卷 版-02；来源提交＝commit 溯源，与发布号分记。
- **边界**：组件内部版本策略（fixed 锁定／independent 独立）是产品内容层事实，PMO 不治理，只要求对外发布号唯一；不引进治理层（避免另造档位参数）。
- 格式须正则可查，进 #20 执法（含产品发布版本 SemVer 格式）；字符串前缀等实例参数项目初始化定，实例化自由、可查性不自由。

### 阶段卡结构（#5）

**是什么**：每阶段一张统一结构的方法卡；标准化落在卡结构统一，agent 按卡执行不自行发明流程。

**五字段**：

- **入口条件**：可检查的前置——上游产出物已生效（#3）＋上游门禁通过；不满足不进卡。
- **动作**：本阶段做什么，逐步列；共用事项只引用通则卷统一项，不另定义。
- **产出物及模板**：用哪个 assets 模板生成，强制上游引用头部（#6）。
- **出口判据**：可检查——写明查什么文件、对什么字段；不许空泛标准；通过才进下一阶段。
- **裁定点**：哪些须用户裁定（#7），哪些 agent 可自决；高风险挂项目卷 权-03。

**规则**：十卡共用本结构；门禁判据机械可查部分进 #20 执法；卡内不重复通则，定位读当前卡不整卷读入。

### 产出物头部格式（#6）

**是什么**：每份产出物强制头部字段；回溯不靠 agent 自觉。

**强制字段**：

- 产出物 ID（沿用〈类型码-序号〉，如 D-001，与 R/C/G 分码，#1）
- 所属阶段
- 需求 ID（上游需求，贯穿 ID 链 #1）
- 上游引用（上游产出物 ID＋版本；强制，不空）
- 文档状态（#3 词表）
- 交付物版本（#4）
- 生成时间／来源提交（身份，项目卷 版-02）

**规则**：上游引用字段强制，缺即门禁不过（#20 执法查头部）；启动阶段产出物无上游产出物时，上游引用写"启动·用户目标"或等效来源，不空；头部机械可查，hook 校验字段齐全与上游存在。

### 状态板结构（#9）

**是什么**：项目续接唯一入口；新会话先读它。

**节**：

- 当前阶段（十阶段之一）
- 当前结论（一句话：能不能继续、主线范围）
- 待裁项（列表，各附呈报指针）
- 阻塞项（列表，各附原因与处置口径）
- 打断与回归（被什么打断、重入类型与重入点，#8）
- 下一步（一句话）
- 唯一交付物身份指针（指向项目卷 版-02 三件套誊录）

**规则**：只写当前事实、风险、下一步，不写阶段流水账（项目卷 决-02），更新前先删失效；已交付基线与历史阶段进推进记录/归档，不在状态板；状态板是项目事实，在 governance/，续接唯一入口（项目卷 决-06）。

### 流程图记法（#10）

**是什么**：流程图＋文字双 representation，文本化记法（不用图片）；图管结构（顺序、分支、回退、门禁位置），文字管语义（节点做什么、判据是什么）。

**记法约定**：

- 用 text 代码块；节点写阶段/动作名，`->` 表顺序。
- 分支标条件（`?条件`），回退标目标（`↩ 阶段`），门禁标位置（`〔门：判据指针〕`）。
- 图节点强制映射上游出处（图 ID＋节点 ID，#12）；细节展开成子图不堆一张图。
- **封闭集**：结构符为封闭集，仅此四类（`->`／`?`／`↩`／`〔门〕`），对应顺序/分支/回退/门禁四要素；图内不得自造第五类结构符，新结构类（如并行/汇合）须回本卷增补后方可使用。
- **保留符**：四符号为保留符，不进节点名（防 `?` 在条件节点名里歧义）。
- **出处标注语法**：节点上游出处统一写作 `节点名[源:图ID/节点ID]`，可重复多条（多上游图）、逐条正则解析（#20 图出处／层级／覆盖一致解析此语法）；与 `〔门：…〕` 异括号免混读。
- **括号锚定注记**：节点需求/能力锚可用括号注记；属语义注记非结构符，不进封闭集。

**规则**：各阶段出什么图随阶段卡定；图审批按 #19；记法本卷统一，项目不另发明符号。

## 组件与执法

### 约束包组件分工与执法判据（#20）

**是什么**：五组件分工＋机械/语义执法判据。

**五组件**：

- **rules／声明层**：宪法级硬约束（隔离、写边界、披露、上提、承重条款），短、常驻；方法永不进。
- **skills／方法层**：PMO 本体（三卷）。
- **commands／入口层**：初始化/续接/对账/回溯入口，薄壳调路由。
- **agents／角色层**：独立检查者承重（只读、与生产者分离）；其余预留。
- **hooks／强制层**：执法逻辑宿主无关＋触发绑定宿主相关。

**执法判据**：机械可查→hook；语义判断→rules＋方法。

**初始执法清单**：

- 会话启动读状态板。
- 写入路径权限（四层写读权威，项目卷 权-01；环境层授予字段只走用户通道，#16）。
- 产出物上游引用头部（#6；含版本格式正则可查——需求/交付物/产品发布版本三轨格式，#4）。
- 图出处／层级／覆盖一致（#12／#19）。
- 生效状态有决策记录（#21 信任根）。
- 决策记录写入通道：写入＝裁定协议 #7 步 3 专属动作；写入须可追溯到用户裁定；hook 校验生效项与决策记录一一对应。

**降级**：缺位组件显式降级写回执，不许静默；触及承重执法走 #21 降级纪律。
